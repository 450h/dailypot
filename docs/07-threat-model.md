# 07 — Security threat model

**Assets:** the user's financial history (sensitive personal data, on their own PC); the integrity of the money figures; the trustworthiness of the published installer.
**Trust boundaries:** (1) renderer ↔ main IPC; (2) files that enter the app (imports, restored backups, a tampered `data.json`); (3) the release pipeline ↔ the downloader.
**Not in scope:** an attacker with admin/malware on the user's PC. They can read `%APPDATA%` and keylog anything. We say so plainly.

| # | Threat | Vector | Impact | Mitigation (where) |
|---|---|---|---|---|
| T1 | **Renderer compromise → code execution** | Injected markup in a note/name rendered unsafely; malicious content in an imported file | Full PC access if Node is reachable | React escaping only, no `dangerouslySetInnerHTML`; `contextIsolation`, `sandbox`, `nodeIntegration:false`; strict CSP (`default-src 'self'`); the preload exposes only typed commands; IPC sender validated; navigation and new windows blocked; production builds load from a custom privileged `app://` protocol (with the CSP sent as a response header), not `file://`; a null `senderFrame` is rejected. Follows the [Electron security checklist](https://www.electronjs.org/docs/latest/tutorial/security) (accessed 2026-10-13, **High**). |
| T2 | **Malicious import / backup file** | User imports a crafted JSON | Crash, corrupted state, prototype pollution, huge memory use | Size cap (50 MB); the path comes only from a main-process dialog; `JSON.parse`, then migrations, then **full zod validation with strict objects (unknown keys rejected)**; referential checks; a summary and confirmation; a `pre-import` backup before replacing. Restore only accepts names matching `^(data-\d{4}-\d{2}-\d{2}\|pre-(import\|restore\|migration)-\d{8}T\d{6})\.json$` that resolve inside the backups folder (no path traversal). |
| T3 | **Data loss / corruption** | Crash or power loss mid-write; antivirus holding the file; disk issues; bad migration; **two app instances writing**; a clock set backwards | Loss of history | Atomic write (tmp + fsync + rename, retried with backoff on EPERM/EBUSY); **single-instance lock** (`app.requestSingleInstanceLock()`; a second launch focuses the first window); 14 daily snapshots taken **before** the day's first write; corrupt file kept as `data.corrupt-<ts>.json`, then the newest valid snapshot is loaded with a banner, or a recovery screen if none is valid (never a silent fresh start); pre-migration backups; a newer-schema file opens read-only; "≤ today" checks run only on IPC writes, never on load (05 §9). |
| T4 | **Casual snooping on a shared PC** | Someone opens the app | Privacy | Optional PIN (scrypt hash + salt in `security.json`, constant-time compare, backoff in main, data commands refused while locked, auto-lock). **Limitation stated in the UI and README:** the PIN doesn't encrypt `data.json`, so anyone with file access can read it. Encryption at rest is OPEN-QUESTIONS D3. |
| T5 | **PIN brute force via the UI** | Repeated guesses | Bypassing the privacy screen | Exponential backoff up to 30s, enforced in main (not the renderer). A 4-digit PIN is still weak, so we recommend 6+ digits. |
| T6 | **Malicious dependency (supply chain)** | Compromised npm package | Code execution on build or user machines | Few dependencies; lockfile committed; `npm ci` in CI; `npm audit --audit-level=high` blocks CI; Dependabot; review install scripts of new deps; versions pinned exactly. |
| T7 | **Fake / tampered installer** | Someone redistributes a trojaned "DailyPot" | User installs malware | Releases only from GitHub Actions on tags; SHA-256 checksums published with each release; README says "download only from this repo's Releases". v1 is unsigned, so there's no publisher identity (OPEN-QUESTIONS D2). |
| T8 | **Data exfiltration by the app itself** | A future change adds a network call | Privacy breach | Production builds block all http(s)/ws(s) via `session.webRequest`; CSP `connect-src 'self'`; no telemetry or auto-update (ADR-0005). A PR that adds network access needs a superseding ADR. |
| T9 | **Wrong money figures** | Float rounding; off-by-one dates; time zones | Bad decisions | Integer minor units; date-only strings; a pure engine with exhaustive unit tests, including the worked example and edge cases (payday 31, Feb, leap years, overspend beyond the pot, early cycle start). |
| T10 | **Electron runtime vulnerabilities** | An old Chromium in a stale build | Exploitable via any content | Keep Electron on a supported major; Dependabot; Electron fuses (SECURITY §11); DevTools disabled in packaged builds. |
| T12 | **CSV formula injection** | A note like `=HYPERLINK(...)` opened in Excel | Spreadsheet-side code or exfiltration | Text cells starting with `= + - @`, tab or CR are prefixed with `'`. Amount cells stay numeric (negative numbers aren't escaped). UTF-8 with BOM. |
| T11 | **`shell.openExternal` abuse** | Renderer passes an arbitrary URL | Launching arbitrary protocols | Only one hardcoded GitHub URL is allowed; the channel takes no URL argument. |

**Logging:** the app writes no analytics. Errors go to a local `logs/main.log` (rotated, ≤ 1 MB). Amounts, notes and PINs are never logged.
